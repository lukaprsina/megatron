● Good catch — this is the real constraint on PCA.

  PCA works on flattened pixel vectors. If the camera angle varies, the same
  good tile looks different each frame, and reconstruction error spikes
  spuriously. PCA is only reliable on geometrically normalized patches.

  The fix is a perspective warp before PCA, not a different model. This is
  exactly what the teammate's tile_detect.py does before passing tiles to their
  classifier — OTSU threshold → contour detection → 4-corner extraction →
  cv2.getPerspectiveTransform + cv2.warpPerspective → canonical fronto-parallel
  patch. Classification happens on the warped image, not the raw camera frame.

  If we implement that warp step (which we need to do anyway to reliably segment
  individual tiles from the conveyor belt), PCA receives aligned, normalized
  patches and the perspective problem disappears. The warp is ~30 lines of
  OpenCV, nothing exotic.

  So the pipeline is:

  arm camera frame
    → OTSU threshold → contour → 4-corner fit
    → warpPerspective → canonical N×N patch
    → PCA reconstruction error → threshold → DEFECT / OK

  The warp is load-bearing. If the fine-positioning phases (LiDAR wall stop,
  Hough tilt correction) don't get the camera close enough to overhead, the
  contour-finding step breaks before PCA even sees anything. So the warp's
  robustness depends on fine-positioning quality.

  Bottom line: PCA is still the right call — but it's contingent on the warp
  working, which is contingent on fine-positioning working. These three
  components live and die together.

  Does that change anything for you, or do you want to proceed with PCA + warp?
